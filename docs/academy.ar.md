# Between Bytes · خمسة مختبرات تطبيقية · 0.9.1

## حالات HTTP للدفع · 0.9.1

الطلب الصحيح يرجع 200. قبول الطلب المخالف في الضعيفة هو الخلل المقصود. في المُصلحة:

| الحالة | النتيجة |
|---|---|
| السعر، الإجمالي، الخصم، الشحن، الضريبة، التقريب والكمية المخالفة | 422، دون تغيير المورد |
| العملة، الإيصال غير المناسب، حالة غير مسددة، الاسترداد أو التجربة غير المسموحين | 409 |
| توقيع إشعار خاطئ | 401 |
| إعادة قسيمة مستهلكة / رصيد هدية غير كاف | 409 عند رفض الجميع؛ 207 لنتيجة جزئية مع operations |
| إعادة إشعار صحيح تمت معالجته | 200، دون استحقاق أو معاملة جديدة |
| حقول مطلوبة ناقصة أو نوع غير صالح | 400 |

استجابة GET 200 في لوحة قراءة السجل لا تعني قبول POST السابق. افحص حالة POST ورمز الخطأ وتغير المورد معاً.


الواجهة الرئيسية تجمع 50 حالة داخل خمسة مختبرات: الدفع 16، XSS عدد 12، الصلاحيات 10، حدود المحاولات 7، والخدمات البرمجية 5. افتح `http://127.0.0.1:8000/` أو `/academy`. الغرف الأساسية القديمة محفوظة في `/foundations`. كل الحالات مفتوحة بلا نقاط.

## تجربة واستجابة فعلية

تختار المختبر ثم الحالة من خريطته. كل حالة لها نسخة ضعيفة وأخرى مُصلحة وحالة خادم مستقلة لكل منهما، حتى لا تخلط أخطاء مختلفة في تجربة واحدة. محرر JSON يرسل الجسم نفسه إلى مسار التطبيق الظاهر في معاينة HTTP، دون غلاف case/input. ترويسة X-Forwarded-For الفعلية تحمل تسمية المصدر المختبرية عند وجودها. لا يتغير IP جهازك.

```http
POST /academy/api/payment/pay-binding/fixed HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json

{"payment":"settled-order1"}
```

يرجع الخادم HTTP 409 فعلياً مع error.code=payment_order_mismatch؛ ليس 200 يحتوي status=409 داخل JSON. الخادم يضيف X-Request-ID وETag للطلب المحفوظ. تقييم التمرين، والفحوص والعلم، تؤخذ من `/academy/evidence` ولا تختلط بجسم استجابة التطبيق.

## الدفع: ماذا ينفذ محلياً؟

المحرك يحتفظ بطلب وبنود وأسعار وعملة ومجموع مستحق، ومبالغ محصلة ومستردة، وسجل معاملات واستحقاقات تحميل ورصيد هدية واشتراكات. طلب GET مستقل إلى `/academy/resource?case=pay-binding&mode=fixed` يقرأ الحالة الحالية؛ revision يتغير عند معاملة مقبولة ويبقى كما هو عند رفضها. سجل المعاملات مقيد إلى 80 إدخالاً والاشتراكات إلى 20، والأموال وحدات صحيحة.

من جولة جديدة، جرّب الإيصال غير المرتبط بالطلب في الضعيفة ثم المُصلحة، وافحص المورد بعد كل طلب، ثم أرسل الإيصال الصحيح للمُصلحة. الدفع الصحيح السابق يبقى صحيحاً عند رفض طلب لاحق؛ لا يجب أن يؤدي الرفض إلى التراجع عن معاملات صحيحة. تعديل عرض سعر وحده لا ينشئ عملية تحصيل ولا يثبت شراءً مجانياً.

إيصالات المزود سجلات محلية محددة، وإشعار webhook يستخدم تحقق HMAC-SHA256 فعلياً على حدث معياري ثابت. المثال السليم يحمل توقيعاً صالحاً من بيانات المختبر المنشورة. لا توجد بطاقات ولا بوابة دفع خارجية ولا أموال حقيقية. المحرك ليس بروتوكول مزود إنتاجي، ولا بديل قاعدة بيانات بمعاملات وقفل موزع. حالة الهدية تُحاكي ترتيب قراءة قديمة بشكل حتمي، وليست اختبار سباق شبكة.

## المختبرات الأخرى

الصلاحيات تستخدم فواتير ومؤسسات وهوية alice مثبتة على الخادم. التعديل والحذف يغيران بيانات الجولة فعلياً؛ النسخة المُصلحة ترفض قبل التغيير ولا تسرب المحتوى المرفوض. حدود المحاولات تعيد 401 عند وصول محاولة فاشلة للتحقق و429 عند الحظر، مع Retry-After وRateLimit-Remaining. سقف التجربة ثلاث محاولات، والمصادر نطاقات توثيق فقط والوقت في حالة الحافة ساعة مختبرية صريحة.

XSS يضم 11 سياق تنفيذ داخل iframe بأصل مبهم وCSP تمنع الموارد والاتصالات الخارجية، وحالة URL لفحص href وسياسة المخطط فقط دون ادعاء تنفيذ. توجد 36 صيغة حمولة ومقارنة، منها أمثلة خاملة عن قصد. المخزّن يحفظ تعليقاً ثم يعرضه GET مستقل؛ DOM يقرأ location.hash وsearch فعليين. ترصد إشارة alert بدلاً من نافذة؛ غياب الإشارة في نافذة المراقبة ليس برهان غياب جميع XSS.

SQLi يشغل SQLite حقيقية في الذاكرة. NoSQL ينفذ شرط مستند مقيداً محلياً؛ القالب يحلل حساباً مقيداً دون eval. SSRF والتحويل يستخدمان موارد وسياسات مغلقة بلا DNS أو نقل خارجي. علامة الإنجاز والعلم أدوات تعلم وليست شهادة أو اختباراً مانعاً للغش.

### تأكيد دفع من الواجهة · `pay-status`

```python
if body["status"] == "paid": release_download()
```

```python
receipt = provider_ledger.lookup(receipt_id)
```

### مصدر إشعار الدفع · `pay-webhook`

خدمة الدفع تستقبل حدث settled من مزود محلي تجريبي. النسخة الجديدة تتحقق فعلياً من HMAC-SHA256 لحدث معياري محفوظ على الخادم. المثال السليم يحمل توقيعاً صحيحاً لهذا الحدث فقط؛ تغيير التوقيع إلى invalid يمثل إشعاراً غير موثوق.

إشعار عميل يحمل event=settled يعامل كإشعار مزود.

في الضعيفة قد ينشأ استحقاق مع صفر مبلغ محصل. في المُصلحة التوقيع الخاطئ يعطي 401 ولا يغير السجل. هذا عقد مختبر ثابت وليس بروتوكول Stripe أو Adyen؛ في الإنتاج يُتحقق من الجسم الخام والطابع الزمني وإعادة الإرسال وفق عقد المزود.

الفكرة الضعيفة:

```python
if event == "settled": fulfil(order)
```

الفكرة بعد الإصلاح:

```python
require_constant_time_hmac(canonical_event, signature)
apply_verified_event_once()
```

تحقق من توقيع المزود خارج بيانات العميل ثم طبّق الحدث مرة واحدة.

الطلب الصحيح:

```json
{
  "event": "settled",
  "signature": "53ad32f960cb08a9887152a7542d36f80df5b92d831e9af5b6e3c29f459ff812"
}
```

طلب التحقيق:

```json

  "event": "settled",
```

عندك طلب order100 بسعر 100 دولار وإيصال settled-order1 صحيح لكنه لطلب ثان بقيمة دولار واحد. وجود إيصال ناجح لا يكفي إن لم يرتبط بالطلب الجاري.

دفعة صحيحة لطلب رخيص تستخدم لتسوية طلب أكبر.

من جولة جديدة قارن order.id مع payment_order، ثم captured_amount مع amount_due. الضعيفة تمنح التحميل مقابل دولار واحد. المُصلحة تعطي 409 ولا ترفع revision. أرسل settled-order100 بعدها لتثبت أن الدفع الصحيح ما زال يعمل.

```python
require(receipt.order_id == order.id)
require(receipt.amount == order.total and receipt.currency == order.currency)
```

### ترويسة مصدر يحددها العميل · `rate-xff`

المفتاح هو مصدر وهمي من حقل الطلب؛ تغييره ينشئ سلة جديدة.

```python
bucket = normalized_account_id; trusted_peer_policy()
```
