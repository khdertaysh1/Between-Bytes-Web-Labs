# Bilingual local rooms (0.7)

Every one of the 13 lessons now has an application-themed workspace: account support, access, recovery mail, invoices, administration, server search, DOM preview, profile preferences, account API, checkout redirects, link previews, client assets and deployment files. The workspace is an interface over the documented local handlers, not a cloud VM or a production clone of a training platform.

## Arabic and English

Use the language button in the header. It switches the interface, room descriptions, learning explanations, objectives, hints, checks and result labels. English is left-to-right; Arabic is right-to-left. Language preference and optional completion marks are stored locally. Switching language reloads the view: an unfinished evidence notebook is not retained, so begin a new round. Raw HTTP fields, API responses and synthetic technical identifiers retain their protocol spelling. No external translation service or CDN is used.

English prose is authored in `english.js`; shared interface messages are in `i18n.js`. Arabic learning content remains in the original lesson catalogs. Dynamic UI strings pass through `tr`, while new workspace messages use explicit bilingual alternatives. Add and test both editions when extending a lesson.

## Investigate rather than watch

Read the scenario, start a practice round, use the application form, inspect the latest response and evidence notebook, then repeat against the fix. The application panel names the fictional service and shows the actual local origin. It does not pretend that a public external service is running.

The HTTP workbench builds an actual local form-encoded request from application inputs. For the nine HTTP-handler rooms you can edit the body and supported forwarded header, then replay the request to the current lesson endpoint. It refuses external URLs, other room paths, changed Host values, duplicate/unsupported fields and arbitrary session or Origin headers. The browser remains responsible for its own cookies and actual Origin.

XSS, CSRF and CORS require browser behavior. These four rooms use the application inputs and isolated/second-origin workflows; their inspector shows captured browser evidence instead of pretending a raw request proves execution or cross-origin readability.

## Per-browser classroom state

Starting a round creates/reuses an opaque HttpOnly/SameSite classroom cookie. Each browser cookie has separate synthetic counters, mailbox, note state, CSRF session and room journal. Tabs in the same browser profile share that cookie and can interfere. Distinct browser profiles do not share those counters.

The in-memory store has a maximum of 32 classroom contexts and a 30-minute idle expiry. Restarting the Python process clears them. Completion marks and language remain in browser storage. This is local application-state separation in one process, not OS/container isolation, hosted multi-tenant infrastructure or production authentication. Keep the app bound to loopback as supplied.

## What the server verifies

`/rooms/status` reports checks based on responses actually generated by the local handlers during the active room. It does not accept a client-submitted list of successful HTTP actions. A bounded 120-event journal tracks only the current room; no cookie or CSRF-token values are added to the evidence journal. Starting a new round clears the journal and rotates its synthetic flag.

For server-observed rooms, meeting the local criteria reveals a fresh `BB{...}` flag from server state. Flags represent the documented model, not actual exploitation of an external product, a grade or a certificate.

XSS and CORS are explicitly `browser-assisted`: the server can observe preview delivery or origin-policy requests but cannot prove JavaScript execution or response readability from those requests alone. Those rooms still require the browser evidence checklist. The server report never emits a server-only flag for them and explicitly describes this limitation. The client-side completion checklist remains inspectable and is not an anti-cheating system.

## Existing scope is preserved

All rooms remain open; there are no points or prerequisite locks. Synthetic SSRF transport performs no network fetches, redirect exercises display policy decisions rather than navigating externally, exposed files come from an in-memory fixture table, and API keys are intentionally nonfunctional. The actual two-origin CSRF/CORS exercises remain same-site loopback examples. See [advanced scope](advanced.en.md).

## Checks

```bash
python -m unittest discover -s tests -v
node tests/progression.test.cjs
```

With Playwright/Chromium and a running local app:

```bash
node tests/browser.cjs
BB_TEST_LANGUAGE=en node tests/browser.cjs
node tests/bilingual.cjs
```

Coverage includes all 13 workflows in both languages, full English text across room tabs, language persistence/direction, restricted raw-request replay, browser-session separation, journal/flag boundaries, mobile overflow and the existing browser-origin isolation checks. Node and Playwright are development tools only; normal Termux use still needs Python and Git.
